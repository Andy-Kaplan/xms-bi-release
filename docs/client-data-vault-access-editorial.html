The Method
Three movements
01.

We ingest.

Any operational system with an API or data feed — transactions, movements, people, customers, assets, events. New sources are added through a standard onboarding pattern, not a custom build each time.

02.

We conform.

Every source feeds the same standardised entity model. A "product", "location" or "transaction" means the same thing regardless of which system it came from — and the model is designed to absorb new business domains as your operation evolves.

03.

You query.

Connect Power BI, Tableau, Looker, Metabase, Python, dbt — or anything that speaks SQL — directly to your dedicated database. No middleware, no exports, no waiting for IT.

Where you connect

Two layers, one connection

Connect once. Pick the layer that fits the question. Most teams use both — the Data Vault for bespoke analysis, the Presentation layer to skip a lot of joins.

Layer 01 — Foundation

The Data Vault

Industrial-strength, fully historised model of your business reality. Every change to every record is tracked with effective-from / effective-to dates. Nothing is overwritten, nothing is lost.

  • i. Conformed entities spanning sales, inventory, workforce, surveys and CRM.
  • ii. SCD Type 2 history — query state as it was on any date.
  • iii. SHA-256 hash keys — deterministic joins, integration-agnostic.
  • iv. Source-of-truth for any custom mart, KPI or ML feature you want to build.
Layer 02 — Accelerator

The Presentation Layer

Pre-built fact and dimension tables — flattened, indexed, ready to drop straight into a BI tool. The same tables we use to power the XMS dashboards.

  • i. Fact tables — line-item sales (15-min grain), product margin, inventory counts / usage / sales by day.
  • ii. Dimensions — 3-tier hierarchical (location, product, occasion, deal, channel, …).
  • iii. Calendar & forecast tables for period-over-period and target tracking.
  • iv. No SQL gymnastics — designed for self-service BI.
III.
The entity model

What’s in the Vault

A snapshot of the entity model today, grouped by business domain. Hubs are the things your business runs on; events are what happens to them, with full timestamped history. Every entity is fully relatable to every other — and the model is built to grow.

Hub — a thing your business runs on (e.g. Product, Location, Customer) · Event — something that happened, with a timestamp (e.g. Sale, Stock movement) · Domain — a business area; new ones plug in without rebuilding the model
IV.
Access

How access works

Built around the same isolation, security and refresh model that runs the XMS product.

01.

Your own database

Every organisation lives in a dedicated SQL Server database. No shared tables, no row-level filtering to worry about — only your data is in your database.

02.

Read-only by design

You receive a scoped login with read access to the Data Vault and Presentation schemas. The pipeline keeps writing on its schedule; nothing you do can affect it.

03.

Scheduled refresh

Data lands on a recurring cadence (typically multiple times per day). Every record carries a load timestamp, so freshness is always visible in your queries.

04.

Full historisation

The Data Vault never forgets. A price change, a renamed location, a moved employee — all preserved with effective-from / effective-to dates.

05.

Schema stability

The entity model is versioned. Additive changes are the norm; breaking changes are rare, announced, and supported with a deprecation window.

06.

Documented

You get the same internal reference docs we use — entity catalogue, ER diagrams, integration coverage matrix, source-of-truth definitions.
