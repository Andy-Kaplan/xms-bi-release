Overview

XMS BI Platform

XMS BI is a multi-organisation analytics platform running on SQL Server Managed Instance. Each organisation gets an isolated database provisioned from a shared control plane, which holds all integration definitions, Data Vault entity schemas, deployment objects, and visualisation templates. Data is ingested from external APIs on a scheduled basis (refresh frequency is configurable per integration) and flows through a fixed pipeline: raw landing tables → typed staging → CDC-detected load tables → Data Vault 2.0 storage (HUB/SAT/LNK/SAT_LNK) → flattened presentation tables → parameterised dashboard queries. The platform is configuration-driven — Data Vault structures, staging pipelines, and presentation tables are generated automatically from definitions stored in the control plane, rather than being hand-authored per organisation.

⇄ End-to-End Data Flow

Data moves through six discrete layers, each with a distinct responsibility and isolated in its own schema within the per-organisation client database. The early layers normalise and type raw API data; the CDC layer detects what has actually changed; the Data Vault layer historises changes in a hub-satellite-link model; and the presentation layer flattens that history into query-ready fact and dimension tables.

🏗 Database Layout

The platform uses two database tiers. A single core database acts as the control plane for the entire fleet — it holds organisation registrations, integration definitions, entity schemas, and visualisation templates. Each organisation gets its own isolated database, named {prefix}_XMS_{GUID}, which is provisioned automatically when the organisation is registered. The organisation database contains all integration-specific schemas, the full Data Vault store, presentation tables, and the objects that serve and populate them. Both databases carry a core schema, but they serve different purposes: in the control plane it holds platform management objects; in the organisation database it holds the ELT stored procedures that run the data pipeline (staging, CDC, Data Vault loading, presentation builds) as well as the visualisation stored procedures that serve dashboard queries.

⚙ Core Control Plane

The core database is the single source of truth for all platform configuration. It contains two schema types: the core schema, which holds the eight control tables, triggers, functions, and management procedures documented below; and one int_{name}_{ver} schema per registered integration, which holds that integration's StagingControl, EntityMappings, and GlobalParameters records. This separation means integration configuration is namespaced and self-contained — adding a new integration creates a new schema, it doesn't add rows into a shared config table. The control plane drives the deployment engine: when a organisation is mapped to an integration, the platform reads definitions from here to provision the correct structures in the organisation database.

🚀 Deployment Engine

The deployment engine solves a core multi-tenancy challenge: keeping stored procedures and functions consistent across an arbitrary number of organisation databases without manually scripting each one. The solution is to store all deployable object definitions as SQL text in the DeploymentObjects control table, with a {SCHEMA} placeholder substituted at deploy time. When sp_DeployObjects runs, it iterates all active objects in ExecutionOrder, resolves each organisation's database name, substitutes the schema placeholder, and executes the SQL against the target database via USE [db] EXEC('...'). This means deploying an updated procedure to all organisations is a single sp_DeployObjects call — not 50 individual script runs.

CREATE TABLE [core].[DeploymentObjects] (
    ObjectID         INT IDENTITY(1,1),
    ObjectName       NVARCHAR(255),     -- e.g. 'sp_DataVaultLoad'
    ObjectType       NVARCHAR(50),      -- PROCEDURE | FUNCTION
    SchemaName       NVARCHAR(128),     -- target schema (usually 'core')
    Category         NVARCHAR(50),      -- grouping category
    Description      NVARCHAR(500),     -- human-readable description
    CreationScript   NVARCHAR(MAX),     -- full CREATE/ALTER SQL
    DropScript       NVARCHAR(MAX),     -- optional DROP SQL
    ExecutionOrder   INT,               -- 1-48 tables/functions, 49-64 card procs
    IsActive         BIT,
    Version          INT
)

sp_DeployObjects iterates active objects in ExecutionOrder, resolves each database name, replaces {SCHEMA} placeholder, executes via USE [db] EXEC('...'), and logs success/failure per object per database.

🏭 Data Vault 2.0 Implementation

Data Vault 2.0 is the storage methodology used for all integrated data in XMS BI. It organises data into three structural types: HUBs store business keys (one row per unique entity, hash key only); SATs store the attributes of those entities with full SCD Type 2 historisation (every change is retained with LOAD_TS, EFFECTIVETO, and CURRENT_FLAG); and LNKs store relationships between entities as append-only records, with optional SAT_LNKs holding attributes of the relationship itself. All hash keys are SHA-256 VARBINARY(32) values derived from business keys. The 84 entities in XMS BI span hubs, binary links, ternary and quaternary links, self-referencing links, and build-state tracking links — all defined in the DataVaultEntities control table and generated automatically by sp_GenerateDataVaultTables.

👥 Organisation Provisioning

Provisioning a new organisation is a three-stage process: create the organisation, register the integration, then map the two together. Each stage is distinct because organisations and integrations exist independently — an integration can be shared across many organisations, and a organisation can be mapped to multiple integrations. The provisioning flow is trigger-driven: inserting into the core control tables fires AFTER INSERT triggers and SQL Agent jobs that handle database creation, schema generation, Data Vault table building, and object deployment automatically. The steps below show the correct sequence using the Add* stored procedures.

Use the Add* procedures

🔌 Integration Framework

Once registered, an integration's behaviour is entirely defined by three configuration tables in its int_{name}_{ver} schema in the core database. StagingControl defines every transformation step from raw landing data to the staging layer, including the SQL to execute and the tier order to run it in. EntityMappings tells the Data Vault loader which staging columns map to which entity attributes, which columns are business keys requiring SHA-256 hashing, and which columns trigger Type 2 historisation when changed. GlobalParameters holds the DDL for each DL landing table (used at provisioning time) plus any integration-specific runtime config values. Together these three tables are the complete specification of an integration — no transformation logic lives in application code.

⚒ Staging Process

The staging process transforms raw landing data into typed, cleaned records ready for Data Vault loading. All DL table columns are NVARCHAR(MAX); staging applies type casts, deduplication, business logic, and joins to produce the stage.* tables that the load procedures consume. Staging tables are fully rebuilt on each run using a DROP / SELECT INTO pattern — there is no incremental merge. Steps are defined in StagingControl and executed in tier order by sp_Staging: tiers allow later steps to join against the output of earlier ones. Before staging begins, sp_ProcessStagingDuplicates removes duplicate rows from all DL tables using ROW_NUMBER() partitioned by business columns.

IF OBJECT_ID('stage.NCR_CHANNEL_LINK', 'U') IS NOT NULL
    DROP TABLE [stage].[NCR_CHANNEL_LINK];
SELECT * INTO [stage].[NCR_CHANNEL_LINK] FROM (
    SELECT DISTINCT CONCAT_WS('-', [storeId], [dob], [id]) AS HEADER_SRC_KEY,
        CASE WHEN [takeOutOrderId] IS NULL THEN 'Pos' ELSE [revenueCenter_Label] END AS CHANNEL
    FROM [int_ncraloha001].[DL_SALES_STREAM]) AS source_query;

📦 Data Vault Loading

Data Vault loading is orchestrated by sp_DataVaultLoad, which iterates every integration schema that has StagingControl records and runs the full pipeline for each one. For every entity defined in EntityMappings, the load sequence is: populate the intermediate load.{Entity} table from staging, update delta tracking parameters, classify changes via CDC, then write to the Data Vault using either sp_ProcessHubSat (for hub entities) or sp_ProcessLink (for link entities). The load.* tables are the bridge between staging and the Data Vault — they hold the current batch of records with computed hash keys, ready for change comparison. The SQL to populate each load table is dynamically generated from EntityMappings at runtime, so no hand-authored load queries exist.

sp_DataVaultLoad
  For each int_% schema with StagingControl:
    sp_ProcessStagingDuplicates (DL_* dedup)
    sp_Staging (produce stage.* tables)
    For each Load step:
      sp_PopulateLoadTable (fill load.ENTITY)
      sp_UpdateEntityDeltaParameters
      sp_GenerateCDC (classify changes)
      sp_ProcessHubSat (hub entity) | sp_ProcessLink (link entity)
-- UploadEntityMappings generates:
INSERT INTO [load].LOCATION (HUB_ID, LOCATION_ID, ...)
SELECT HUB_ID, LOCATION_ID, ... FROM (
    SELECT ..., ROW_NUMBER() OVER (PARTITION BY HASHBYTES(...) ORDER BY (SELECT NULL)) AS rn
    FROM stage.NCR_LOCATION) sub WHERE rn = 1

🔍 CDC Detection

XMS BI uses a CHECKSUM-based CDC mechanism rather than database transaction log capture. For each entity, sp_GenerateCDC compares the current batch of records in load.{Entity} against the active rows in datavault.SAT_{Entity} (where CURRENT_FLAG=1), computing two independent checksums per row. CHECK_TYPE1 covers all tracked columns; CHECK_TYPE2 covers only the columns designated for Type 2 historisation. The combination of these two checksums determines the change classification, which is written to load.CDC_{Entity} for consumption by the hub/satellite and link processing procedures.

CodeMeaningCondition
NNew recordNo matching HUB_ID in SAT
T1Type 1 changeCHECK_TYPE1 differs, CHECK_TYPE2 same — overwrites, no history
T2Type 2 changeCHECK_TYPE2 differs — closes current row, inserts new history row
NCNo changeBoth checksums match — updates soft-delete flags only
 
INSERT INTO load.CDC_{ENTITY}
SELECT ISNULL(LH.HUB_ID, RH.HUB_ID),
    CASE WHEN RH.HUB_ID IS NULL THEN 'N'
         WHEN LH.CHECK_TYPE1 != RH.CHECK_TYPE1 THEN
             CASE WHEN LH.CHECK_TYPE2 != RH.CHECK_TYPE2 THEN 'T2' ELSE 'T1' END
         ELSE 'NC' END AS CHANGE_TYPE
FROM (SELECT HUB_ID, CHECKSUM(...) CHECK_TYPE1, CHECKSUM(...) CHECK_TYPE2
      FROM load.{ENTITY}) LH
LEFT JOIN (SELECT HUB_ID, CHECKSUM(...) CHECK_TYPE1, CHECKSUM(...) CHECK_TYPE2
           FROM datavault.SAT_{ENTITY} WHERE CURRENT_FLAG=1) RH ON RH.HUB_ID=LH.HUB_ID

🔨 Hub & Satellite Processing

sp_ProcessHubSat handles all four CDC change types for hub entities in a single atomic transaction. The sequence is designed around the requirement that Type 1 changes overwrite without creating history, while Type 2 changes close the current row and insert a new one. For new records (N), any orphaned HUB entries are cleaned up before the fresh insert. For Type 1 changes (T1), the original EFFECTIVEFROM date is preserved before the stale SAT row is deleted and re-inserted with updated values. For Type 2 changes (T2), the current row is closed by setting EFFECTIVETO and CURRENT_FLAG=0, and a new row is appended. For no-change records (NC), soft-delete flags are reset to reconcile any records that reappeared in the source after being absent.

StepActionCDC
1UPDATE EFFECTIVEFROM dates for T1 (preserve originals)T1
2DELETE from SAT for T1 and N (remove stale before re-insert)T1N
3DELETE from HUB for N (remove orphaned entries)N
4Close T2 records: SET EFFECTIVETO, CURRENT_FLAG=0T2
5INSERT N, T1, T2 records into SATNT1T2
6INSERT new N records into HUBN
9Reset IS_DELETED=0 in SAT for NCNC
10Reset IS_DELETED=0 in HUB for NCNC

🔗 Link Processing

Link processing is fundamentally simpler than hub/satellite processing because relationships in Data Vault 2.0 are immutable — once a link between two entities is recorded, it is never updated or closed. sp_ProcessLink is therefore append-only: it removes any records from the load batch whose LNK_ID already exists in the LNK table, then inserts only the genuinely new relationship records. Where a SAT_LNK exists for a link (holding attributes of the relationship itself), those attribute records are inserted in a separate step after the link rows are written.

  1. DELETE from load where LNK_ID already exists in LNK
  2. INSERT remaining new records (hub ID columns + LOAD_TS + SRC)
  3. If SAT_LNK exists, INSERT attribute records separately

🛠 Presentation Deployment

DeployPresentationTables builds or rebuilds the presentation layer in a target organisation database. It reads all Live table definitions from the PresentationTables control table, creates the presentation schema if it doesn't exist, then drops and recreates each presentation table by executing the stored DDL. It is safe to re-run because the presentation layer rebuilds entirely from Data Vault data via sp_ProcessPresentation — but be aware it does drop existing presentation tables on each run. It runs automatically during organisation provisioning and can also be called manually to redeploy after a schema change. The @DryRun flag lets you preview which tables would be affected without executing anything.

PROCEDURE [core].[DeployPresentationTables]
    @DatabaseName NVARCHAR(128), @DryRun BIT=0, @ContinueOnError BIT=1, @LogResults BIT=1

Cursors over PresentationTables where status='Live' and DDL not null. Creates schema if needed, drops existing table, executes DDL, logs results per table.

📊 Presentation Tables

The presentation layer is the query-ready surface that dashboard queries read from directly. It flattens the normalised Data Vault hub-satellite-link model into dimensions, fact tables, and supporting tables. The layer is rebuilt by sp_ProcessPresentation, which executes the SQL steps defined in PresentationControl in tier order. Dimension tables use a 3-tier hierarchy (BOTTOM / MIDDLE_1 / TOP) constructed via recursive CTEs from SAT data, with names resolved through COALESCE(MICROSERVICE_NAME, native_NAME) to support entities that may be sourced from multiple integrations. A sentinel value of CONVERT(BINARY(32), -999) is used throughout to enable null-safe joins between dimensions and facts on BOTTOM_HUB_ID. Fact tables use a delete-append load pattern. Each fact table is driven by a specific Data Vault time-series entity; the query must declare @StartDate and @EndDate variables sourced from that entity's start and end date parameters in core.GlobalParameters, join to the CALENDAR table, and filter calendar rows on those date variables.

📈 Visualisation Queries & Cards

VisualisationQueries holds all parameterized SQL templates that power the dashboard. Each record defines a query for a specific card type; the card type determines which visualisation stored procedure executes it. Queries use a WHERE 1=1 @FilterClause placeholder — the executing procedure builds the filter clause dynamically from the user's filter selections and injects it at runtime. Every query returns two result sets: the data rows consumed by the chart or grid, and a metadata result set containing the card title, description, trend value, and supplementary metadata. Filter queries (FilterList card type) are a special category — they return dimension values used to populate the filter dropdowns in the dashboard UI rather than rendering a chart.

⚙ Key Conventions

  • Hash keys — VARBINARY(32) SHA-256 via core.SHA256Hash(). Hash value 1 = salted with integration schema (business key); hash value 2 = unsalted; hash value 0 = pass through.
  • Dimension hierarchies — 3-tier BOTTOM / MIDDLE_1 / TOP with BOTTOM_HUB_ID joins; COALESCE(MICROSERVICE_NAME, native_NAME) name resolution
  • Sentinel values — CONVERT(BINARY(32), -999) for null-safe dimension joins
  • Entity type detection — no underscore = Hub; underscore = Link (name parts identify connected hubs)
  • Entity lifecycle — Build → Live → Retired — only Live entities included in table generation
  • Database states — PENDING → CREATING → ACTIVE → FAILED → INACTIVE → MAINTENANCE → ARCHIVED
  • Dynamic SQL — metasql pattern (USE [db] EXEC('...')) and three-part sp_executesql
  • CDC codes — N = new, T1 = Type 1 change (overwrite, no history), T2 = Type 2 change (close + insert new row), NC = no change (CHECKSUM-based detection)
  • DL table columns — All NVARCHAR(MAX) + LOADTS_UTC + INT_FETCH_DATE system columns
  • FilterClause injection — WHERE 1=1 @FilterClause pattern; filters defined in FilterDefinitions JSON
  • Dual-result pattern — Result set 1 = data rows; Result set 2 = header metadata (title, description, trend value, and supplementary metadata)
