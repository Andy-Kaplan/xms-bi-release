### Rules any NEW Growyze card must inherit (all now enforced by `99_verify_plan2.sql` §A)
Each was a measured defect, not a precaution. All 15 deployed datasets comply; a new card that breaks one gets caught.
1. **Carry the resolver** — the CTE joining the org's `sys.schemas` to `core.core.Integrations` on `IntegrationType = 'POS'`, with `int_growyze001` as fallback. Join on `product.[BOTTOM_SRC]` for `F_PRODUCT_MARGIN_DAY` (it has no `SRC` column), on `F.[SRC]` for `F_LINEITEM_15MIN`, on `sp.[SRC]` for `SAT_PRODUCT`. **Inventory cards do not use it** — they scope to `int_growyze001` via `invitem.[BOTTOM_SRC]`.
2. **Never filter `BOTTOM_LEVEL_NAME`** — it is `'Product'`/`'Location'` for Growyze but **`'BOTTOM'` for Mews and NCRAloha**, so it silently drops every POS row. Scope by `BOTTOM_SRC` instead.
3. **Category grain is `COALESCE(TOP_MICROSERVICE_NAME, TOP_NAME)`**, and `FilterDefinitions.ProductCategories` must sit on the **same grain as the `GROUP BY`**. Mews `TOP` = 12 real categories vs `MIDDLE_1` = 98 product families; NCRAloha 2 vs 8; Growyze `TOP` ≡ `MIDDLE_1`.
4. **Always `CAST(<date col> AS DATE)` on `CALENDAR` joins.** `F_PURCHASES_DAY.ORDER_DATE` carries a time on **every** row; `COUNT_DATE` and `F_LINEITEM_15MIN.ORDER_DATE` are midnight-only today, so an uncast join works by luck.
5. **Set `ParameterMappings = N'{"StartDate":"C.[DATE]","EndDate":"C.[DATE]"}'`** — the date picker derives its columns *only* from there. The one exception is a FilterList, which has no date window. See `memory/feedback_date_filters_via_parametermappings.md`.
6. **Keep any ratio's numerator and denominator on one coverage.** `SUM(PROFIT)` NULL-skips uncosted rows while `SUM(NET_VALUE)` counts them all — unguarded, Oak & Vine read 63.7% instead of 82.9%. Put the guard **inside the aggregates**, not the `WHERE`, when the card needs to tell "no sales" apart from "no cost data".

### Hard-won operational notes (keep)
- **Verify vis queries against the ORG database, never from `core`.** The resolver reads `sys.schemas` of the *executing* database, so a three-part-prefixed run from `core` resolves *core's* schemas, finds no `int_*` POS schema, and silently returns the Growyze fallback for every org — **a false PASS on the one thing most worth checking**.
- **Never value inventory on `THEO_QTY`** until [O33](O33-inv-counts-day-movement-fanout.md) is fixed. The count fan-out makes it differ between duplicate rows (230 of Padel's 259 groups), so a `ROW_NUMBER` tie picks arbitrarily and the figure moves between renders — observed £17,777.76 vs £17,534 for the same org and data. Use `ACTUAL_COUNT` deduplicated to count grain.
- **Never re-add a `location <> 'Unknown'` guard to the Deliveries card** — [O36](O36-growyze-purchases-no-location.md). It discards the `-999`-sentinel rows, which on Dirty Sixth is 60% of real delivery spend.
- **A snapshot is not a cross-period `SUM`.** Take each item's latest count (`RN=1`); summing every count date overstated Padel Earls Court 9.5× (£23,369 vs £221,695). **Ibis Gloucester returns the identical number either way**, so it cannot detect this — verify on Padel's 34 count dates. See `memory/feedback_degenerate_acceptance_org.md`.
- **Verifier hygiene, now learned three times on this item.** `96_verify_plan1.sql` shipped three checks that could never pass; `41`'s negative check was a structural tautology; and `99_verify_plan2.sql`'s first draft reported a confident PASS over **zero** datasets because every check was written as "0 offending rows ⇒ PASS". Count what you *inspected*, not only what you rejected, and report `VACUOUS`/`N/A` when an org cannot falsify the claim.
- **Don't assert equality against a recorded baseline in a verifier.** Padel's Plan 1 figure had already drifted (£148,897.95 / 7,600 vs the recorded £144,248.29 / 7,489) because a load landed after sign-off — while Oak & Vine and Dirty Sixth still matched to the penny, which is how we know it is real data movement and not a query difference. Hardcoding it would have baked in a permanent false FAIL. The honest gate is running the verifier **before and after** a deploy and diffing.
- **"Presentation rebuild" is NOT part of `sp_DataVaultLoad`** — `core.sp_ProcessPresentation` is separate, and its **Fact** steps are gated by a load window (`LINEITEM_START/END`, `STOCKEVENT_START/END`) in each org's own `core.GlobalParameters`, which rests at NULL between loads. `BETWEEN NULL AND NULL` matches nothing, so a naive rebuild is a silent no-op; **Dimension** steps truncate-and-rebuild unconditionally. `97_rebuild_presentation.sql` handles the widening and always restores NULL. *(Not needed for vis-query changes like Plan 2 — those take effect at the next card render.)*
- **`UploadStagingControl` does not exist.** `UploadEntityMappings` is the only `Upload*` proc in `core`, and its parameter is **`@intSchema`**, not `@IntegrationSchema`. Staging steps are read straight from `StagingControl.query_sql`, so a staging edit needs no regeneration call.
- **Task 6 deviation is approved and live**: `LINEITEM_TIMESTAMP` comes from `DL_SALES.createdAt` (UK local), not the plan's `sale_from`, which is date-only.
- **Intra-day coverage is permanently partial on Growyze orgs.** Only ~14% of Padel's PROD lines carry a timestamp (1,496 of 10,890) because `DL_SALES` is a rolling window — history's source data no longer exists and never backfills. `GrowyzeSalesHeatmap`'s Description says so. POS-sourced orgs are unaffected (Oak & Vine 176,412 of 176,412).
- **Resolver design caveats, inherited unchanged:** it keys off **schema presence, not `OrganisationIntegrations.IsEnabled`**, so a disabled POS integration would still suppress the Growyze fallback (no org is in that state today); and the fallback literal `int_growyze001` is hardcoded, so an `int_growyze002` would fall through to empty.
