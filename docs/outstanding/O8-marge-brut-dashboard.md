- **2026-07-30 — date filter did nothing; fixed (`live/18_date_filter_parameter_mappings.sql`, DEPLOYED + verified end-to-end).** Changing the dashboard's date range changed no card — all of them kept showing every month.
  - **Root cause: the date filter was wired to the wrong one of the platform's two filter channels.** `core.BuildDynamicWhereClause` takes the date columns from **`ParameterMappings`** (`$.StartDate` / `$.EndDate`) and only emits a predicate when that lookup returns a column. All 9 `MargeBrut*` datasets shipped with **`ParameterMappings = '{}'`**, so `@StartDate`/`@EndDate` were **silently discarded** — no error, no empty card. `14` had instead invented a `FilterDefinitions` key `PeriodMonth`, which exists on these 9 datasets and **nowhere else in the platform** (enumerated all 35 distinct filter keys across every LIVE record — not one other is date-typed). Nothing emits it, and an `IN`-list is the wrong shape for a range picker. Left inert.
  - **The obvious mapping would have been wrong.** `PERIOD_MONTH` is always the 1st, so mapping both slots to it drops the opening month of any mid-month range — measured 15 Jun→15 Jul: naive = 6 rows/£15,078.11/cost NULL (**June gone**) vs overlap = 12 rows/£32,216.82/27.3%. Both agree on whole months, so the naive version would have passed a casual test and failed in the user's hands — the same normalisation bug already fixed once in `99_verify` check 3. Mapped instead to the month-overlap test `EOMONTH(PERIOD_MONTH) >= @StartDate AND PERIOD_MONTH <= @EndDate` (the engine concatenates the mapped values verbatim, so expressions work with no engine change).
  - **The supplier card carried a live `datetime2` trap.** `F_PURCHASES_DAY.ORDER_DATE` is `datetime2`; mapping `EndDate` to the raw column compares against midnight and drops the whole last day — **16 lines / £129.45** for June, the exact figure already on record for this table. Both slots mapped to month-derived (time-free) DATE expressions, which also keeps the card month-aligned with the other seven so a mid-month pick can't make it disagree with the Purchases KPI.
  - Also stripped the literal `@FilterClause` from two SQL **comments** (one from `14`, one from `16`): the card SPs inject via `REPLACE`, which substitutes inside comments too. Harmless only while the clause was always empty — this change makes it non-empty for the first time.
